# 澄清清单（什么时候问、问什么、怎么追问）

## 什么任务必须先澄清

命中任意一条就先提问再规划：

- 「效果」类主观诉求（好看/好用/太烂了）——不问清就是瞎猜方向；
- 有多个可行方案或取舍（留/删/改、换栈/不换、拆/不拆）；
- 会推翻既有决策或架构（如「重做」「大改」）；
- 涉及权限、数据归属、谁能改什么；
- 验收标准含糊，或上一轮「机器绿但用户不满意」。

一两步能说清、无取舍、无主观效果诉求的小任务：跳过提问，在计划的「默认假设（可推翻）」里写明你的理解直接出计划。

## 提问清单（一轮不超过 5 个问题）

### H1 痛点：到底烂/缺在哪
给分类选项（视觉/性能/交互/结构/排版/响应式/其他）让用户多选 ＋ 自由补充。痛点就是本轮范围，没拿到清单不动手。

### H2 边界：做多深
- 逐模块问「留 / 删 / 重做 / 只调观感」；
- 「重做」要问清是重写实现还是只调效果；
- 新旧功能取舍单独立项。

### H3 验收口径
- 量化指标：给具体数字（首屏 <1.5s、响应 <100ms、无横向滚动…）；
- 主观闸门：用户明确说「可以」才算过；
- 脚本/测试类证据要求。

### H4 技术栈与架构拍板
- 给对比表（方案 × 维护性/成本/风险）＋ 明确推荐；
- 用户给的判据与给定选项矛盾时（例：「要好维护」却排除了最优解），**摆出矛盾重新推荐**，而不是顺着选项硬选。

### H5 权限 / 数据归属 / 非功能
- 谁可看、谁可改（角色划分）；
- 数据存哪（前端本地/后端持久化）、是否统一下发；
- 性能预算、兼容范围（做不做移动端等）。

### H6 运行模式：单对话还是多对话并行
- 用户说「同时开几个」「并行」「多对话」「一人公司」即多对话模式：追问包切分（一对话一包）、合流顺序、谁有发布权。
- 没说就是单任务默认，不追问，直接出计划。

## 追问策略

1. 含糊答案（「都行」「1 或 3」「你定」）不许直接采纳成决策——追问一次；用户明确让你定的，写清判据后代为拍板并标注「代拍板」。
2. 用户的自由补充（custom 文本）逐字读，通常含真需求；与选项冲突时以补充文本为准再确认。
3. 一次问不完分多轮；每轮聚焦一个主题。
4. 提问优先用带选项（含推荐标注）的提问工具，方便用户点选；开放式缺口再让用户补充。
