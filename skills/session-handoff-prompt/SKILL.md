# 会话交接提示词

## 为什么需要它

换对话继续做时，新对话看不到旧对话的任何上下文。只丢一句「继续优化」，新对话就得重新侦察
服务器、重新读 `.agents/`、重新踩一遍已经踩过的坑，而且很容易把上一轮**没验证过的结论**
当成既成事实继续往上盖。

这个项目已经吃过一次亏：REQ-007 声称「核心已修复、50 并发全绿」，实际根因是
`_inflight_lock` 自死锁，一直没被发现，用户连着反馈了十几轮。事后复盘写进了
`.agents/progress/milestones.md` 的 M15「结论更正」。

所以交接提示词的真正价值不是「复述做了什么」，而是**把已经花时间查清楚的事实变成新对话的起点，
同时把没查清的东西标成待验证，不让它冒充事实**。

## 铁律

1. **只写有证据的结论**。每条事实要么附命令/输出的出处，要么明确标成「待验证」。
   绝不能把推测写成「已完成」或「已修复」。
2. **历史记录不等于事实，关键项必须现场复核**。`.agents` 里的旧结论会过期：本项目的
   「`verify_portal.py` 64/64 全绿」「`portal-snapshot` 常年红」两条记录，在交接时现场复核
   都和当时的表述不符。凡是新对话要依赖的结论（服务状态、验收基线、配置取值、参数名），
   都要在生成提示词时重新跑一遍；跑不了的要标成「未复核」。
   复核还有一个前提：**先确认没有别的任务在同一台服务器上并发跑**，否则量到的红项是自己造成的。
2. **产物是文件**，不是聊天里的一段话。落在工作区根目录，文件名形如
   `<主题>-继续优化提示词.md`。写完用 present 交付给用户。
3. **必须带上 `.agents` 回写条款**：提示词里要写清「开工前先读哪三份文件」和
   「收工后必须把本轮工作写回哪里」。这是用户反复强调过、也最容易被漏掉的一条。
4. **不美化进度**。没做的事写「未开始」，被推翻的结论写「已推翻」，服务常年红就写红。

## 生成步骤

### 第一步：只读采集

| 采集什么 | 从哪里 |
|----------|--------|
| 需求编号与状态 | `.agents/progress/requirements.md` |
| 架构决策编号 | `.agents/progress/decisions.md` |
| 里程碑编号与当前阶段 | `.agents/progress/milestones.md` |
| 本轮改动的文件与哈希 | 工作区文件 + 服务器实际文件（两边都要） |
| 服务与验收现状 | 服务器上的 `systemctl is-active`、验收脚本输出 |
| 阻塞项 | `milestones.md` 的阻塞记录 + `requirements.md` 的待用户提供信息 |

编号必须现场读出来，不要凭记忆写。写错编号会让新对话找不到东西。

### 第二步：分三类

把手上所有信息分成三类，分别放进不同小节，**不允许混写**：

- **已确认的事实**：有命令输出、日志、文件哈希或代码行号支撑。
- **待验证的假设**：写成「判定步骤」，不要写成结论。例如写
  「H1：跑 `curl ... force=1` 后看 `rev` 是否变化；若不变再看 `refreshError`」，
  而不是写「刷新失败是因为上游限流」。
- **阻塞项**：需要用户提供信息或做选择的，单独列出，标明卡在谁那里。

### 第三步：按模板写文件

模板见下一节，小节一个都不能少。写完后用第八节的清单自查一遍再交付。

### 第四步：交付

把文件路径给用户，并用两三句说清「这一轮真正改变了什么」。不要复述文件内容。

## 提示词模板

```markdown
# <项目名> · 继续优化提示词（新对话用）

> 使用说明：把「提示词正文」整段发给新对话。开工前先读 .agents/progress 下三份文件。

## 提示词正文（复制从这里开始）

# 角色与任务

# 服务器与部署事实（必须遵守）
含：连接方式、路径映射、部署命令、验收命令、硬约束

# 当前状态
含：.agents 最新编号（REQ / ADR / M）、已完成、进行中、待开始

# 已确认的事实（带证据）

# 待验证的假设（写成可执行的判定步骤）

# 首批工作包
每个工作包写：根因 / 改哪些文件 / 验收口径

# 后续路线

# .agents 更新要求（强制）
开工先读三份；收工必须回写 requirements / milestones / decisions；
格式遵循 .agents/rules/830-progress.md

# 已知环境坑

# 明确不做的事

# 完成判定

（提示词正文结束）
```

## 边界情况

| 情况 | 怎么处理 |
|------|---------|
| 用户只是问「为什么 X」 | 先回答为什么，再问是否需要落成交接提示词。不要硬产出文件 |
| 会话里有没验证的结论 | 只能进「待验证」，绝不能进「已完成」 |
| 本地与服务器哈希不一致 | 在提示词里标成第一优先项，说明后果是「改了但没生效」 |
| 项目当前没有未完成项 | 只写事实表与 `.agents` 回写要求，不硬凑工作包 |
| 不确定 `.agents` 最新编号 | 现场读三份文件，不要靠记忆 |
| 子代理或新对话看不到本会话 | 提示词必须自带服务器事实与路径，不能假设对方知道 |
| 用户对上一轮不满 | 如实写进提示词，包含根因与「为什么之前的判断错了」，别粉饰 |

## 自查清单

交付前逐条过：

1. 模板要求的小节一个不缺。
2. 写了「收工必须回写 `.agents/progress/`」，并指明读哪三份、遵循哪条规则。
3. 「已确认」与「待验证」分开，没有混写。
4. 每条已确认事实都能追溯到命令输出、日志、哈希或代码行号。
5. 与服务器实际状态不矛盾（哈希、服务状态、验收结果）。
6. 文件落在工作区根目录，并通过 present 交付。
7. 没有把推测写成已完成。
