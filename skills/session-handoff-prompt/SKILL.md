# 会话交接提示词

## 为什么需要它

换对话继续做时，新对话看不到旧对话的任何上下文。只丢一句「继续优化」，新对话就得重新侦察环境、
重新读项目文档、重新踩一遍已经踩过的坑，而且很容易把上一轮**没验证过的结论**当成既成事实继续往上盖。

真正值钱的交接不是「复述做了什么」，而是两件事：

1. 把已经花时间查清楚的事实变成新对话的起点；
2. 把没查清的东西**明确标成待验证**，不让它冒充事实。

第 2 点尤其重要。真实案例：某项目交接文档写着「核心已修复、50 并发全绿」，实际根因是后台线程
里的一把不可重入锁自死锁，问题一直没解决，用户连着反馈了十几轮。事后复盘写进了里程碑的
「结论更正」。**交接文档里一句不诚实的「已完成」，代价是下一轮几个小时的返工。**

## 铁律

1. **只写有证据的结论**。每条事实要么附命令/输出/文件哈希/代码行号的出处，要么明确标成「待验证」。
   绝不能把推测写成「已完成」或「已修复」。
2. **历史记录不等于事实，关键项必须现场复核**。项目文档里的旧结论会过期——服务状态、验收结果、
   配置取值、参数名、文件路径，都可能在某次改动后失真。凡是新对话要依赖的结论，生成提示词时
   重新跑一遍；跑不了的要标成「未复核」。
   复核有个前提：**先确认没有别的任务在同一台机器上并发跑**，否则量到的失败可能是自己造成的。
3. **产物是文件**，不是聊天里的一段话。落在工作区根目录，文件名形如 `<主题>-继续优化提示词.md`。
   写完用 present 交付给用户。
4. **必须带上回写条款**：写清「开工前先读哪几份文件」和「收工后把本轮工作写回哪里」。
   这是最容易被漏掉、也是下次交接质量的决定性一环。
5. **不美化进度**。没做的写「未开始」，被推翻的写「已推翻」，服务红了就写红。
6. **母版零任务内容**。具体项目的事实（服务器地址、路径、账号、密钥文件名）只进本次提示词正文，绝不进本文件。

## 运行模式（单任务默认，多对话可选）

- **单任务模式（默认）**：一份提示词交接一个任务，按下面步骤直出。
- **多对话并行模式（用户说「多对话」「并行」「一人公司」时启用）**：每个任务各写各的提示词；公共事实只写引用指向（如「见主 ledger 索引」），不复制全文，避免两份分叉；每份 must 含 Git 与并行状态小节（分支、文件锁归属、主干与线上是否一致）。

## 生成步骤

### 第一步：只读采集

| 采集什么 | 从哪里 |
|----------|--------|
| 需求编号与状态 | 项目进度目录（如 requirements.md，现场确认实际路径） |
| 架构决策编号 | 同上，`decisions.md` |
| 里程碑编号与当前阶段 | 同上，`milestones.md` |
| 本轮改动的文件与哈希 | 工作区文件 + 目标机器实际文件，**两边都要** |
| 服务与验收现状 | 现场跑服务状态命令、验收脚本 |
| Git 状态 | 当前分支、未提交改动、与主干差异、文件锁归属 |
| 阻塞项 | 进度目录里的阻塞记录、待用户提供信息表 |

编号必须现场读出来，不要凭记忆写。写错编号会让新对话找不到东西。
如果项目没有 `.agents/` 这类目录，就先看有没有 README / CHANGELOG / 计划文档，用现有的替代。

### 第二步：分三类

把手上所有信息分成三类，**不允许混写**：

- **已确认的事实**：有命令输出、日志、文件哈希或代码行号支撑。
- **待验证的假设**：写成「判定步骤」，不要写成结论。例如写
  「H1：跑 `curl ... force=1` 后看 `rev` 是否变化；若不变再看 `refreshError`」，
  而不是写「刷新失败是因为上游限流」。
- **阻塞项**：需要用户提供信息或做选择的，单独列出，标明卡在谁那里。

### 第三步：按模板写文件

模板见下一节，小节一个都不能少。写完用「自查清单」逐条过一遍再交付。

### 第四步：交付

把文件路径给用户，并用两三句说清「这一轮真正改变了什么」。不要复述文件内容。

## 提示词模板

```markdown
# <项目名> · 继续优化提示词（新对话用）

> 使用说明：把「提示词正文」整段发给新对话。开工前先读 <进度目录> 下的几份文件。

## 提示词正文（复制从这里开始）

# 角色与任务

# 环境与部署事实（必须遵守）
含：连接方式、路径映射、部署命令、验收命令、硬约束

# 当前状态
含：最新编号（需求 / 决策 / 里程碑）、已完成、进行中、待开始

# Git 与并行状态（如在用）
含：当前分支、未合流分支、文件锁归属、主干与线上是否一致

# 已确认的事实（带证据）

# 待验证的假设（写成可执行的判定步骤）

# 首批工作包
每个工作包写：根因 / 改哪些文件 / 验收口径

# 后续路线

# 进度目录更新要求（强制）
开工先读哪几份；收工必须回写哪几份；遵循哪条格式规范

# 已知环境坑

# 明确不做的事

# 完成判定

（提示词正文结束）
```

## 写工作包的原则

工作包是交接文档里最容易被写废的部分。三条经验：

- **根因已确认的才写成「可直接动手」**，其余标「先判定再改」。判定的步骤要具体到命令。
- **验收口径必须是可执行的**，例如「本地与目标机器文件哈希一致 + 服务 active + 验收脚本全绿」，
  而不是「功能正常」。
- **把「先修工具再改功能」单独列成工作包 0**。如果验收套件本身不可信（结果不稳定、必须特定权限
  才能跑、会改动被测服务），那么后面所有「通过」都没有意义，必须先修它。

## 边界情况

| 情况 | 怎么处理 |
|------|---------|
| 用户只是问「为什么 X」 | 先回答为什么，再问是否需要落成交接提示词。不要硬产出文件 |
| 会话里有没验证的结论 | 只能进「待验证」，绝不能进「已完成」 |
| 工作区与目标机器哈希不一致 | 标成第一优先项，后果是「改了但没生效」 |
| 项目当前没有未完成项 | 只写事实表与回写要求，不硬凑工作包 |
| 不确定最新编号 | 现场读进度文件，不要靠记忆 |
| 子代理或新对话看不到本会话 | 提示词必须自带环境事实与路径，不能假设对方知道 |
| 用户对上一轮不满 | 如实写进去，包含根因与「为什么之前的判断错了」，别粉饰 |
| 用户给了硬约束（如产物必须放某目录） | 按用户的约束执行，并在交付时说明与默认约定的差异 |
| 多对话并行中 | 每个任务各写各的提示词；公共事实只写引用指向，不复制，避免两份分叉 |

## 自查清单

交付前逐条过：

1. 模板要求的小节一个不缺。
2. 写了「收工必须回写进度目录」，并指明读哪几份、遵循哪条格式规范。
3. 「已确认」与「待验证」分开，没有混写。
4. 每条已确认事实都能追溯到命令输出、日志、哈希或代码行号。
5. 关键结论是**本轮现场复核**过的，不是照抄旧文档。
6. 与目标机器实际状态不矛盾（哈希、服务状态、验收结果、分支状态）。
7. 文件落在工作区根目录，并通过 present 交付。
8. 没有把推测写成已完成。
9. 本文件和本次产物里没有混入其他项目的具体事实。
